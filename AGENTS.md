# Agent Instructions — TACE.Oracle.Admin

Generated by `Scripts\Export-AgentInstruction.ps1` from `Docs\standards\`. Do not edit
by hand: change the standard, then regenerate. A static test fails when this file
does not match the standards.

These are the rules this repository is held to. They apply the same way to code
written by a person and code generated by an AI. Each rule is one sentence and one
example, with an ID and what enforces it: *Linter* and *Test* are checks the gate
runs; *Review* needs judgement, and a reviewer checks it.

## Checking your work

Run `.\Scripts\Invoke-Gate.ps1 -Unit` before you report a change as done. It runs the
analyzer, the static tier, secret scanning and the unit tier. A change is done only
when every check passes.

## Coding Standards

Source: `Docs\standards\coding.md`.

### Repository layout

- **C-28** — Module source lives under `Source\`: `Source\Public\` for exported functions, `Source\Private\` for helpers, and `Source\Classes\` once a class exists. A build merges it, classes then private then public, into one `.psm1` under `Output\<Module>\<version>\` with a generated manifest. That built module is what is tested and released.
  Example: `Source\Public\Get-RmanBackupStatus.ps1` ships inside `Output\TACE.Oracle.Admin\0.2.2\TACE.Oracle.Admin.psm1`; `Tests\`, `Docs\` and `Scripts\` never ship. *Test.*
- **C-29** — The manifest lists exported functions explicitly, and the list equals the file names in `Source\Public\`; a function is exported if and only if it lives there.
  Example: `FunctionsToExport = @('Get-OracleDatabaseList', 'Set-OracleEnv', ...)`, never `'*'`. *Test.*
- **C-30** — A command alias is declared with an `[Alias()]` attribute on the public function it targets, never with `Set-Alias`, and is listed in the README's Aliases table. The build generates `AliasesToExport` from those attributes.
  Example: `[Alias('oraset', 'oraenv')]` below `[CmdletBinding()]` in `Invoke-OraEnv`. *Test.*
- **C-32** — A script in `Scripts\` is named Verb-Noun with an approved verb and a singular noun, and its `.NOTES` declares how it is invoked: `**Invocation:**` followed by `Standalone`, `Session-scoped`, `Helper` or `lib helper`, and one line of detail. A dot-sourced helper lives in `Scripts\Lib\`.
  Example: `Scripts\Invoke-UnitTest.ps1` with `**Invocation:** Standalone — self-contained; safe to run with pwsh -File.`. *Linter.*

### Language and structure

- **C-01** — Every `.ps1` file starts with `#Requires -Version 7.6`.
  Example: line 1 of `Source\Public\Set-OracleEnv.ps1`. *Linter.*
- **C-02** — Every function sets strict mode and stop-on-error as its first statements.
  Example: `Set-StrictMode -Version Latest` then `$ErrorActionPreference = 'Stop'`. *Linter.*
- **C-03** — One function per file, and the file is named for the function.
  Example: `Source\Private\Set-RestrictiveAcl.ps1` defines only `Set-RestrictiveAcl`. *Linter.*
- **C-04** — Function names use approved PowerShell verbs.
  Example: `Get-RmanBackupStatus`, not `Fetch-RmanBackupStatus`. *Linter.*
- **C-05** — Every function declares its output type.
  Example: `[OutputType([PSCustomObject])]` directly below `[CmdletBinding()]`. *Linter.*
- **C-06** — A state-changing public function supports `ShouldProcess`.
  Example: `[CmdletBinding(SupportsShouldProcess, ConfirmImpact = 'High')]` on `Remove-RmanObsoleteBackup`. *Linter and Test.*
- **C-33** — In `Source\`, every call to a cmdlet that accepts `-WhatIf` decides what a preview does with it. Either it sits inside `if ($PSCmdlet.ShouldProcess(...))`, or it comes after an early return when `ShouldProcess` declines, or it passes `-WhatIf` explicitly. `-WhatIf:$false` marks work that must happen even during a preview, such as creating a default config or removing temporary files. Without one of these, a caller's `-WhatIf` reaches the call and silently skips it.
  Example: `New-Item -Path $configDir -ItemType Directory -Force -WhatIf:$false` in `Get-OracleBackupConfigStore`, which creates the default config as part of reading it. *Linter.*
- **C-07** — A platform-specific function checks the platform first and returns `Success = $false` anywhere it does not support.
  Example: `if (-not $IsWindows) { return [PSCustomObject]@{ Success = $false; Data = $null; Message = 'Windows only.' } }`. *Test.*
- **C-08** — Platform is detected with `$IsWindows`, `$IsLinux` or `$IsMacOS`, never from environment variables.
  Example: `if ($IsLinux) { ... }`, not `if ($env:OS -eq 'Windows_NT') { ... }`. *Linter.*

### Parameters

- **C-09** — Every parameter has an explicit type.
  Example: `[string]$DatabaseName`, never `$DatabaseName`. *Linter.*
- **C-10** — Every parameter of a public function has a type and at least one `[Validate*]` attribute, except switches and credential types.
  Example: `[ValidateNotNullOrEmpty()] [string]$DatabaseName`. *Linter.*

### Statements

- **C-11** — A call with several parameters uses splatting, never backtick line continuation.
  Example: `$params = @{ Path = $path; Encoding = 'UTF8' }` then `Set-Content @params`. *Linter.*
- **C-12** — A pipeline result that is used as an array is wrapped in `@()`.
  Example: `$running = @($services | Where-Object { $PSItem.Status -eq 'Running' })`. *Review.*
- **C-13** — A value that can be an array is passed to `ConvertTo-Json` with `-InputObject`, never piped.
  Example: `ConvertTo-Json -InputObject @($items) -Depth 5`. *Review.*
- **C-14** — Paths are built with `Join-Path`, never by joining strings with `\` or `/`.
  Example: `Join-Path -Path $oracleHome -ChildPath 'bin'`, not `"$oracleHome\bin"`. *Linter.*
- **C-15** — Every file write names its encoding.
  Example: `Set-Content -Path $path -Value $text -Encoding UTF8`. *Linter.*
- **C-16** — Code that edits an existing config file keeps that file's line endings.
  Example: a file read with CRLF endings is written back with CRLF. *Test.*
- **C-17** — The current pipeline item is written `$PSItem`, never `$_`.
  Example: `"Failed: $($PSItem.Exception.Message)"`. *Linter.*
- **C-18** — No emojis in code, scripts or output; status uses a `[LABEL]` prefix.
  Example: `Write-Host '[ERROR] SID not found.'`. *Linter.*
- **C-31** — `PSAvoidUsingWriteHost` stays enabled. A function whose purpose is terminal interaction may use `Write-Host` only with a `SuppressMessageAttribute` on that function stating why; every other function reports through its return object, `Write-Verbose` or `Write-Warning`.
  Example: `[Diagnostics.CodeAnalysis.SuppressMessageAttribute('PSAvoidUsingWriteHost', '', Justification = 'Interactive terminal wrapper: ...')]` on `Invoke-OraEnv`. *Linter.*

### Output contract and error model

- **C-19** — Every public function returns a `PSCustomObject` with exactly `Success`, `Data` and `Message`.
  Example: `[PSCustomObject]@{ Success = $true; Data = $record; Message = 'Backup found.' }`. *Test.*
- **C-20** — A caller checks `Success` before it uses `Data`.
  Example: `if ($result.Success) { $result.Data.AgeHours }`. *Review.*
- **C-21** — A private helper reports failure by throwing a terminating error whose message is already scrubbed.
  Example: `throw "RMAN process invocation failed: $safeMessage"`. *Test.*
- **C-22** — A public function throws only when its parameters are invalid; every other failure is caught, scrubbed and returned as `Success = $false`.
  Example: a missing `rman.exe` returns `Success = $false` with a message; it does not throw to the caller. *Test.*
- **C-27** — When `ShouldProcess` declines, under `-WhatIf` or a "No" at `-Confirm`, a function changes nothing and returns `Success = $true`, `Data` with `Applied = $false`, and a Message that starts with `WhatIf:` and says what would have happened. A real run returns `Applied = $true`, and a Message that reports a change is built only inside the `ShouldProcess` block.
  Example: `Set-OracleEnv -SID ORCL -WhatIf` returns `Success = $true`, `Data.Applied = $false` and `WhatIf: would set ORACLE_SID to 'ORCL'.`. *Test.*

### Help and comments

- **C-23** — Every public function has comment-based help with `.SYNOPSIS`, `.DESCRIPTION`, `.PARAMETER` for each parameter, `.EXAMPLE`, `.OUTPUTS` and `.NOTES`.
  Example: the help block above `Get-RmanBackupStatus`. *Linter.*
- **C-24** — A security requirement in a comment or `.NOTES` block carries the `[SEC]` tag.

## Security Standards

Source: `Docs\standards\security.md`.

How each mechanism is built in this module is described in [SECURITY.md](Docs/SECURITY.md).
This file states the rules.

### Credentials

- **S-01** — A password parameter is typed `[SecureString]` or `[PSCredential]`, never `[string]`.
  Example: `[PSCredential]$Credential`. *Linter.*
- **S-02** — A password reaches an Oracle tool through stdin only, never in the argument list.
  Example: `$process.StandardInput.WriteLine(...)`, with `$psi.Arguments` holding no credential. *Test.*
- **S-03** — Plaintext is extracted from a secure value inline at the stdin write, and is never assigned to a variable.
  Example: `WriteLine("CONNECT TARGET $user/$(ConvertFrom-SecureStringToPlaintext -SecureString $pw)@$alias;")`. *Review.*
- **S-04** — Source code holds no credentials, connection strings or TNS entries.
  Example: a connection alias arrives as a parameter or from the config file, never as a literal. *Linter.*

### What leaves a function

- **S-05** — `Message` on a return object holds no password, no credential value and no value derived from one, on any code path.
  Example: `Message = "DELETE OBSOLETE failed for 'CDB1'."`. *Test.*
- **S-06** — Output captured from an Oracle tool is scrubbed before it is returned, stored or logged.
  Example: `$stdOut = Invoke-CredentialScrub -Content $stdOut`. *Test.*
- **S-07** — An exception message is scrubbed before it is re-thrown or placed in `Message`.
  Example: `$safeMessage = Invoke-CredentialScrub -Content $PSItem.Exception.Message`. *Test and Linter.* The linter half is `Tests\Static\ExceptionScrub.Tests.ps1`: every `.Exception.Message` read in `Source\` is an argument of `Invoke-CredentialScrub`. Exception text reached another way, such as `"$PSItem"`, is left to review.
- **S-08** — Verbose output holds no password or credential value at any verbosity level.
  Example: `Write-Verbose "[Invoke-RmanProcess] NamedCredential: user='$($Credential.UserName)'"` logs the user name, never the password. *Test.*
- **S-09** — No function writes an object that carries a credential to the pipeline.
  Example: the `Data` object of an RMAN function has `AuthMode`, not the credential. *Test.*

### Processes and environment

- **S-10** — Environment variables for a child process are set on that process only.
  Example: `$psi.EnvironmentVariables['ORACLE_SID'] = $OracleSid`, never `$env:ORACLE_SID = $OracleSid`. *Test.*
- **S-11** — Text sent to RMAN or SQL embeds only values that were validated as typed parameters.
  Example: a `[datetime]` parameter formatted into a script, never a raw string from the caller. *Review.*
- **S-12** — No assembly is loaded from a remote or user-writable path.
  Example: no `Add-Type -Path` pointing outside `$PSHOME`. *Linter.*
- **S-13** — Security functions use FIPS-compliant algorithms: SHA-256 or stronger, AES-256, never MD5 or SHA-1.
  Example: `Get-FileHash -Algorithm SHA256` when a hash protects integrity. *Linter.*

### Oracle access

- **S-14** — A function that connects to Oracle states the privilege it needs in `.NOTES`.
  Example: `Requires SYSBACKUP or SYSDBA.` *Review.*
- **S-15** — A connection made by automation is attributable to a named account.
  Example: OS authentication under a dedicated service account, not a shared login. *Review.*

### This repository

- **S-16** — This repo is public: no credentials, account identifiers or infrastructure detail are committed, in files or commit messages.
  Example: a placeholder such as `<ORACLE_HOME>` in a document, or a `-S3Bucket` parameter, never a real host or bucket name. *Linter and Review.* The linter half is `Tests\Static\PublicRepoHygiene.Tests.ps1`: account IDs, ARNs, access keys, literal S3 targets, email addresses and private keys. A real name that matches no pattern, and commit messages, are left to review. A cross-check against a private identifier list is deferred until its design is decided across all public repositories (`TODO.md`, Stack 2).
- **S-17** — The committed agent permission files keep every documented deny rule and allow nothing beyond the documented allow rules.
  Example: removing `Bash(git push *)` from the deny list of `.claude/settings.json` fails the gate until `Tests\Lint\AgentPermissions.psd1` and `SECURITY.md` section 12 change with it. *Linter.* The check is `Tests\Static\AgentPermissions.Tests.ps1`; a file may add deny rules.

## Testing Standards

Source: `Docs\standards\testing.md`.

- **T-01** — Tests use Pester 5.
  Example: `Import-Module Pester -MinimumVersion 5.0`. *Linter.*
- **T-02** — Every function, public or private, has its own test file, named for the function, in the folder under `Tests\Unit\` that mirrors its source folder.
  Example: `Tests\Unit\Private\Set-RestrictiveAcl.Tests.ps1` for the private helper `Source\Private\Set-RestrictiveAcl.ps1`. *Linter.*
- **T-03** — A test file groups its tests under these contexts: `Parameter Validation`, `Implementation`, `Return object contract`, `Security`, and `WhatIf support` where the function supports `ShouldProcess`. A test that proves a security invariant may sit in whichever context holds the setup it needs; the `SEC` tag (T-09), not the context, marks it as a security test.
  Example: `Context 'Security' { It 'Message contains no credential fragment' { ... } }`. *Linter.*
- **T-04** — A unit test touches the filesystem only under `TestDrive:\`.
  Example: `$configPath = Join-Path -Path $TestDrive -ChildPath 'config.json'`. *Review.*
- **T-05** — A unit test mocks every Oracle binary and needs no database and no real credential.
  Example: `Mock -CommandName Invoke-RmanProcess -ModuleName TACE.Oracle.Admin -MockWith { ... }`. *Review.*
- **T-06** — A mandatory or type check on a parameter reads the function's metadata, so no test can stop at a prompt.
  Example: `(Get-Command Get-RmanBackupStatus).Parameters['DatabaseName'].Attributes`. *Review.*
- **T-07** — A mock of an Oracle tool returns output captured from the real tool.
  Example: a mocked `LIST BACKUP SUMMARY` uses the real column layout. *Review.*
- **T-08** — Every `Security` context asserts all of these: no password in the argument list; no credential fragment in `Message` on success or failure; none in verbose output; none in a re-thrown error; and no change to the session environment.
  Example: `$result.Message | Should -Not -Match $testPassword`. *Test.*
- **T-09** — A test cited on an invariant's `Test:` line starts its title with the ID of each invariant it is cited for, comma-separated, then says what it proves. A test cited for a security invariant also carries the Pester tag `SEC`.
  Example: `It 'S1, L2 kills a tnsping that runs past TimeoutSeconds and throws' -Tag 'SEC' { ... }`. *Linter.*
- **T-10** — Each test tier has one entry script, `Scripts\Invoke-<Tier>Test.ps1`, that holds its own Pester configuration, resolves every path from its own location, writes NUnit XML results to `Tests\TestResults\<tier>.xml`, and exits 1 when any test or any test file fails (`FailedCount` or `FailedContainersCount`) and 0 otherwise. The tiers are `static` (`Invoke-StaticTest.ps1`, `Tests\Static\`, with the linters it calls in `Tests\Lint\`), `unit` (`Invoke-UnitTest.ps1`, which builds the module first, then runs `Tests\Unit\` recursively against the built module) and `integration` (`Invoke-IntegrationTest.ps1`, `Tests\Integration\*.Integration.Tests.ps1`, local only, behind five guards; also `Invoke-Gate.ps1 -Integration`).

- **T-11** — A test that asserts a call leaves the session environment unchanged sets sentinel values first with `Tests\Unit\Set-EnvironmentSentinel.ps1`, and compares and restores with `Compare-EnvironmentSentinel.ps1` in a `finally` block. Comparing with the value read before the call passes whenever an earlier test has already left the value the call would set.
  Example: `$sentinel = & (Join-Path $PSScriptRoot '..' 'Set-EnvironmentSentinel.ps1')`, then `($changed -join ', ') | Should -BeNullOrEmpty`. *Review.*

The floor is raised when coverage rises, and lowered only by a recorded decision. A command a unit test cannot reach is recorded in `Docs\TODO.md` with its reason, not covered by a test that exists only to run it.
  Example: `[FAIL] coverage: 94.8% of commands (712 of 751), floor 95.0%.` *Test.*
- **T-13** — An integration test file is named `<Function>.Integration.Tests.ps1` in `Tests\Integration\`, connects with OS authentication only, and runs the five guards in `IntegrationTestHelpers.ps1` before it touches a database. A failed guard fails the run; it never skips. Everything a test creates on the database or disk carries the fixed tag `INTEGRATION_TEST` and the name prefix `IT_`, and is removed at the start and end of the file.
  Example: `Assert-IntegrationTestAllowed -Config $script:config` as the first call in `BeforeAll`. *Test.*
- **T-14** — A branch whose changes reach the database through `Source\` ends with a commit of `Tests\Integration\LastRun.json` from a passing run on a clean tree of the commit before it. The file holds no host name, path or SID.
  Example: commit the code, run `.\Scripts\Invoke-IntegrationTest.ps1`, then commit `LastRun.json` alone. *Review until Stack 4, then Test.*

## Invariant Blocks

Source: `Docs\standards\invariants.md`.

A standard applies to every function. An invariant applies to one function: what must
hold before it runs, while it runs, and after it returns or throws.

### Rules

- **I-01** — Every function carries an `# INVARIANTS` comment block as the first thing in its body, directly after `$ErrorActionPreference = 'Stop'`.
  Example: the block in `Source\Private\Invoke-RmanProcess.ps1`. *Linter.*
- **I-02** — A block is written from what the function does today, not from what it is meant to do one day.
  Example: a parameter that is accepted and ignored is recorded as a limitation, not as a guarantee. *Review.*
- **I-03** — Every entry has an identifier made of a section prefix and a number, unique within its function.
  Example: `P1`, `S2`, `R1`, `T1`, `L1`. *Linter.*
- **I-04** — An identifier is never renumbered or reused once assigned.
  Example: when `S3` is retired, the next security entry is `S4` or higher, and `S3` stays retired. *Review.*
- **I-05** — Every entry is followed by a line that names what enforces it, starting with one of `Type:`, `Guard:`, `Test:`, `Static:` or `Limitation:`.
  Example: `Type: Mandatory and ValidateNotNullOrEmpty.` *Linter.*
- **I-06** — Every security entry carries the `[SEC]` tag.
  Example: `[SEC] S1 No password is placed in the process argument list.` *Linter.*
- **I-07** — A block holds no credential value, secret fragment or sensitive path.
  Example: `S1` describes the password rule without quoting a password. *Linter.*
- **I-08** — A change to a function's behaviour updates its block in the same commit.
  Example: adding an authentication mode adds or amends the entries that mode affects. *Review.*

- **I-09** — A `Test:` line gives each test's exact title in single quotes, and the test is in the test file named for the source file. No other test in that file has the same title, so the citation names one test.
  Example: `Test: 'S2 RMAN script must contain NOPROMPT'.` in `Source\Public\Remove-RmanObsoleteBackup.ps1`, with the test in `Tests\Unit\Public\Remove-RmanObsoleteBackup.Tests.ps1`. *Linter.*
- **I-10** — A test is cited only when it would fail if the invariant were broken.
  Example: a test that mocks the function under test proves nothing about that function, and is not cited. *Review.*
- **I-11** — Every entry except a limitation is proven by a test or a static check. A `Type:` or `Guard:` line is followed by a `Test:` or `Static:` line that names the proof.
  Example: `Guard: the finally block.` followed by `Test: 'S2 zeroes and frees the buffer when the conversion throws'.` *Linter.*
- **I-12** — A `Static:` line gives each check's exact title in single quotes. The check is in `Tests\Static\SourceInvariants.Tests.ps1`, its title is unique in that file, and it starts with the function name, then the IDs it proves. A check cited for a security invariant carries the Pester tag `SEC`.
  Example: `Static: 'Invoke-RmanProcess S2 extracts the password only inside the stdin write'.` *Linter.*

### Sections

In this order. A section with no entries is left out.

| Section heading | Prefix | Holds |
|---|---|---|
| `PRE-CONDITIONS` | `P` | What must be true when the function is called |
| `SECURITY INVARIANTS` | `S` | What must never leak or be changed; every entry is `[SEC]` |
| `POST-CONDITIONS` | `R`, `T` | What holds on a normal return (`R`) and when it throws (`T`) |
| `EXECUTION INVARIANTS` | `L` | What holds on every path through the function |

### What enforces an entry

| Keyword | Meaning | An entry with this keyword is proven by |
|---|---|---|
| `Type:` | PowerShell rejects a bad value at the call | The `Test:` or `Static:` line that follows, which shows the attribute is in place |
| `Guard:` | Code in the function body checks or guarantees it | The `Test:` or `Static:` line that follows, which fails if the guard is removed |
| `Test:` | A Pester test asserts it | The named test, which cites the identifier |
| `Static:` | A check of the source proves a "must never" | The named static check |
| `Limitation:` | Not enforced, on purpose; the risk is stated and accepted | Nothing; the entry makes the gap visible |

A `Type:` or `Guard:` line says what enforces the invariant at run time. The proof line
under it says what fails when that enforcement is removed (I-11).

`Test: none yet.` and `Static: none yet.` are allowed. They mark an invariant that is
stated but not proven, and they are the work list for the test and linter stages.
